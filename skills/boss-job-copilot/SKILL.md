# BOSS 求职助手

程序负责搜索参数、网页读取、去重入库和消息操作；你负责理解用户、判断实际职责和写招呼。岗位进度直接看数据库，不另设工作流调度器。没有内置 LLM，不上传简历或提交其他申请。

这是岗位中性的求职流程。目标职业、相邻方向、混合职责和技能要求的宽严，均从当前用户材料与澄清中确定，写在其私有资料中；不因 Agent 使用的工具或其他求职者的经验预设职业方向。

## 从当前工作目录开始

先确认并告知本次数据目录，再读其中的 user/USER.md 及引用。默认使用调用时 cwd 下的 `.boss-workspace/`；用户显式指定 `--workspace` 时使用该目录。脚本用绝对路径运行，cwd 保持用户的工作目录。不从 home、相邻目录、其他会话或备份自动继承资料。

沟通以聊天为主：直接展示易读的分析、方案、问题和招呼，让用户就地确认，不让用户先打开文档才能参与。PROFILE.md 保存背景、项目证据与能力分析，SEARCH_PLAN.md 保存方向和筛选规则，OUTREACH.md 保存话术偏好；原件放 materials/，例句放 examples/。按需沉淀这些资料，不每次回复都重写。USER.md 只留必要交接与资料索引，不逐岗记录结果或反复更新数量。公共 Skill 不带个人信息。

完整求职请求开始时，按 [运行方式](references/operations.md#浏览器和登录) 尽早准备专用浏览器：复用已有 BOSS 页，尚未打开时用 browser open --boss-home，再检查一次登录。未登录就提示用户可在窗口中手动登录，随即继续读取简历、分析项目和澄清策略；不等待“已登录”回复才做材料分析，环境准备或浏览器故障也不阻塞这部分工作。不轮询登录、不提前搜索，方案确认前网页侧只做首页和登录准备。

“只做职业分析”或“暂不打开浏览器”时保留纯本地流程；“只打开浏览器”则调用 browser open，不顺手检查、采集或启动求职澄清。尊重用户正在使用或主动暂停的窗口。

## 理解用户，确认方案

首次求职或改变方向时读 [背景分析](references/intake.md)。理解简历与代表项目/作品，区分事实、推断和缺少证据的能力；只询问会影响求职判断且仍不清楚的信息。可邀请补材料，不强制提供保密原件。

首次读完简历/项目并完成初步分析后，先在聊天中给出一份**职业画像与求职策略确认报告**，让用户同时核对“你把我理解成谁”和“接下来如何找”。报告须展示职业定位、核心优势及项目依据、优先/可接受/不考虑的方向与理由、能力边界与专业技能及工具要求的宽严、地区/薪资/工作制/公司条件、实际搜索范围和一段对外介绍或招呼参考稿。不能只说“简历已看完”加一句优势，再直接列搜索参数；也不能只给 PROFILE 链接。详细结构见 [首次确认报告](references/intake.md#首次确认报告职业画像与求职策略一起核对)。

区分用户硬底线、偏好，以及招聘方可协商的门槛；未知不默认满足或不满足。参考稿优先突出真实优势，允许用户给语气或例子。画像和策略在同一轮确认，不另设画像状态或多加一轮批准。用户要求先看画像时，先完整展示，停在其要求的阶段。

默认以争取机会的宽松口径看整体匹配：主要工作有真实经历支撑、无明确用户硬冲突即可保留；局部技能差距不一票否决。匹配程度由 Agent 按主要职责的重要性综合评估，可给有依据的粗略比例用于说明和排序，不按 JD 条数或脚本算分，不设统一百分比淘汰线。用户明确要求更严格时按其口径。

用户明确认可所展示的画像和策略后才 plan confirm，记录真实原话。上传简历和登录不是确认。同范围续跑沿用已有确认；用户直接修订规则时据其真实指令更新，回显画像/策略受影响的部分，不重复索要已经给出的同一确认。对画像的认可不等于消息发送授权。

画像与策略报告同时简述浏览器准备情况，方便用户阅读报告时完成登录。方案确认后再 check 一次实际页面并读取结果；已登录且页面可用就直接开始采集，不额外要求回复“已登录”。仍需登录或人工验证时才等待用户处理；只回复登录完成而未认可方案时，继续方案澄清。

## 首批 10 个校准，后续每批取 20 个

读 [运行方式](references/operations.md) 的命令示例和 [审查说明](references/review.md)。不创建临时调度脚本、审查凭据、批次游标或任务认领状态。

1. **采集**：按 [搜索参数](references/search.md) 将已确认条件转成配置，先 dry-run 核对 URL。薪资选一个符合目标的网页档位，跨档按期望上端向上选，不拆薪资搜索；实际区间再于库中初筛。每组检索默认最多 10 页，含第一页。程序串行翻页、被动监听 JSON、按岗位 ID 去重。允许漏采，局部失败记录缺口，直接进入已有库审查。
2. **调用脚本取一组**：`jobs --unreviewed --view review --limit 20`；首次校准改为 `--limit 10`。该入口保留列表事实与已有完整详情，不认领任务或改状态。Agent 直接判断，不另写查询、字段裁剪或语义过滤脚本。相关或职责不明的尽量读详情；明确硬冲突或明显无关才排除。列表已能确定薪资低于底线等冲突就记录排除，不再读详情凑数；校准缺额从其他待审岗位补足。列表阶段只做简短判断，不逐岗写文档或先把整库长篇分析一遍。
3. **读详情并判断**：用 `details --ids ...` 串行获取本组候选，结果完成后 `jobs --ids ... --view review` 读取完整 JD、工作地址及列表事实。逐项核对实际工作城市/地址、薪资、公司条件与已确认底线；搜索条件不是每条结果满足条件的证明，公司总部所在地不等于工作地。由你对应用户经历、主要产出、必做职责与加分项，写具体理由；完整 JD 读取失败就记录失败、继续其他候选。
4. **一次保存本组**：将你的判断写入一个可重复使用的私有 JSON/JSONL，`review --file ...` 批量入库。结果、理由、证据、待核实项和招呼保存在数据库。核对 saved、failed、failed_ids 和逐项结果；部分失败时退出码为 1，已保存项保留，只修正并重交失败项。未保存的小批次丢失可以重审，不用增加恢复机制。
5. **首次校准**：用真实样本验证策略。默认完成 10 个详情审查；若出现尚未对齐、会影响结论的新问题，先把具体岗位、判断分歧和建议直接展示给用户，询问其取舍或是否愿意补充经历。涉及项先用 hold 保留，不能擅自从严淘汰；已明确的规则不重复问。没有策略疑问且没有合适可联系者时再补 10 个，直到有至少一个，并完成当前组；不必为等够数量而推迟必要的澄清。用 `outreach preview --ids ...` 查询累计结果，在聊天中展示全部结论、理由、待校准项及拟发送招呼全文。候选耗尽或网页不可用时如实报告；实际发送另按用户明确范围授权。
6. **授权后继续**：先发送首批符合条件者；再按“取 20 个 → 详情与审查 → 批量保存 → 串行发送本组符合条件者”循环。发送遵守实际授权范围，同范围不每批重问。用户指定数量或停止点时优先遵守，否则处理完本轮可处理岗位；不能把初筛完成或一条草稿当成结束。

20 是后续默认取数大小，可通过 --limit 调整，程序不强制上限、批次锁或任务状态；首批 10 个和搜索每组 10 页是各自独立的约定。网页仍串行操作。标题和标签仅辅助理解，禁止关键词、正则或打分脚本代替语义判断；未出现目标关键词、标签为空或名称普通，都不足以证明职责无关。

相似职责沿用相同的已确认口径。涉及主次职责、相邻方向或能力迁移的新取舍，给用户具体样本澄清，涉及项暂存 hold；不能把某项辅助工作或局部技能缺口直接等同于整个职业方向不符。已明确的规则直接执行，后续批次出现真正的新问题也可澄清。

首批结果报告同时附已确认的职业定位和筛选策略简要回顾（含用户后续修订），把实际岗位的保留/排除/待定理由与规则对照，标明偏差和需要讨论的调整。让用户核对策略在真实岗位上是否按原意执行，不能只列结果再问要不要发送。

## 招呼与联系条件

沿用用户确认的结构：**重要优势 → 相关经历或成果 → 岗位具体匹配点 → 邀请看简历或交流**。经历与匹配句可自然合并；保留关键优势，不必每岗重写全文。职责比例等疑问默认留在审查报告。

先判断岗位匹配，再判断活跃。默认本周活跃以内及未知可沟通；明确过久的合适岗位标 matched_inactive。列表 false/缺失不是不活跃证据，粗略标签不是准确登录日期。已保存的审查和暂缓不会因再次采集、在线变化或规则变化自动重开；用户要求重新审查时才恢复指定岗位。

模拟只针对打招呼，详情读取和分析照常；模拟不点击立即沟通。实际授权区分已展示草稿（batch，默认）和用户明确允许的本轮队列（queue），不能扩大。参考稿确认不代替实际消息授权。具体命令见 [招呼流程](references/outreach.md)。

详情是“继续沟通”就跳过，不点击或补发。无 Skill 尝试记录时记 contacted_external（历史/其他方式）；已核实 sent 和 sending/uncertain 保留原来源。不确定只读核实，不自动重发。立即沟通可能打开弹窗或完整聊天页，脚本核对当前会话后发送；完整页 URL 缺 ID 不代表浏览器卡死。不能把按钮点击或平台默认招呼当成定制消息已发送。

## 续用、反馈与结束

新会话先承接用户最新指令和停止条件，再查 `jobs --unreviewed --view review --limit 20` 继续；需要接续已审未发的草稿时查 `jobs --unsent --view review --limit 20` 和 `reviews --ids ...`。首批尚未校准时仍取 10 个。数据库已有结论就是进度，没有需要找回的审查任务或批次状态。

审查时使用当前用户要求，历史结论默认保留。资料、偏好、Skill 升级、时间推移和岗位再次出现都不会自动让旧结论失效；只按用户明确要求用 review-reset 重开指定记录。更新个人资料不重写整库。反馈写对应资料文档，按需生成 report，日常逐岗结果只入库。

首批待校准问题、方案已确认、正在等消息授权等关键交接变化时，给 USER.md 留数句准确说明；续用时结合 plan/outreach status 和数据库核对，清掉过时的“待确认”。用户对本次待定岗位作出明确反馈后继续这些岗位的判断，不自动重审其他历史。preview 默认返回可直接展示的内容，仅保存消息授权所需 JSON 快照；用户要文件时才加 `--out` 导出 Markdown。

页面动作串行、默认至少间隔 5 秒，无小时/每日配额、任务时长或处理数量上限。本地分析不额外等待。登录失效、验证码、平台明确限发或访问拒绝停止网页，用户手动处理后显式检查恢复；局部读取失败继续其他岗位，本地分析可继续。

正常结束留窗，pause 留窗暂停，close 等待专用窗口及后台关闭；restart 用原 profile 重开。空白页不代表未登录：先用 open --boss-home 打开页面，再 check；标签页失联或持续空白可按 [故障恢复](references/operations.md#暂停关闭与故障) 重开一次，尊重用户正在操作或主动暂停的窗口。关闭、暂停、重开不修改岗位、审查或联系记录；请求中断回执不是岗位状态，已有发送尝试保留并只读核实。收尾报告实际完成、未处理和失败情况；不要为补齐漏页反复采集。
