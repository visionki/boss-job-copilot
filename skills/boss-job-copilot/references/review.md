# 首批 10 个、后续 20 个，Agent 审查，结果入库

先读本数据目录的 PROFILE.md、SEARCH_PLAN.md、OUTREACH.md。用户当前要求是本次判断依据；岗位数据和判断保存在 SQLite，不为每个岗位写一份 Markdown，也不维护额外任务状态。

## 列表初筛只决定是否值得进详情

直接用 `jobs --unreviewed --view review --limit 20` 获取一组；首批校准用 `--limit 10`。脚本返回固定审查视图，保留城市、区域、薪资、公司规模等全部列表事实及已有完整 JD/工作地址，不改变顺序、不做语义预选、不占用岗位。无需另写查询或裁剪字段脚本，数量只是参数约定。

结合已确认的地点、薪资及硬条件做简短初筛；相关或职责模糊的尽量进详情。Agent 自己判断语义，不用关键词、正则或打分脚本按职位名排除。未出现某个词、标签为空或标题笼统，都不是职责无关的证据；不能先写脚本筛出一部分再只读它们。

默认不先给整库每个列表岗位写长篇评语。需要排除时保存明确理由；值得进详情的可以直接获取详情，不必先单独提交一条列表结论。需要暂存列表判断时使用 stage=list、decision=hold、next_action=fetch_detail。

列表已明确存在用户硬冲突的岗位，例如同口径薪资上限低于底线，直接保存 stage=list、decision=reject。首批校准的详情缺额从其他待审候选补足，差几个可用 --limit 取几个，不回头给已排除项补详情或改 stage 凑数。

薪资同口径区间有交集（含端点）即保留；整体更高不自动排除，整体更低按已确认的下探或底线处理，见 [薪资规则](intake.md#薪资区间的默认初筛规则)。未知不是零薪资，也不是默认冲突。

区间上限恰好达到用户底线也满足初筛，不再以“主体区间偏低”变相拒绝。用户明确忽略的门槛不能重新成为扣分或拒绝理由；用户底线与招聘事实未知要分开，未写工作制不等于明确不满足。多个待核实项叠加也不能自行变成硬冲突。

## 读取本组详情，再一次提交

下文 PY/BOSS/W 代表实际绝对路径，见 [运行方式](operations.md)。

```text
PY BOSS --workspace W jobs --unreviewed --view review --limit 20
PY BOSS --workspace W details --ids <本组值得看详情的ID...>
PY BOSS --workspace W result --id <请求ID>
PY BOSS --workspace W jobs --ids <本组ID...> --view review
```

details 由程序串行访问，可复用有效缓存；结果已抓取不等于 Agent 已审查。Agent 逐个阅读完整 JD，判断实际产出、必做职责、能力要求与加分项，对应用户的真实项目/作品。不预设任何职业的接受或排除分类；“未展示”不等于“不会”。

每岗同时核对 facts.city/district、detail.work_address、薪资和已确认的公司条件。不得用搜索的城市、公司总部或业务覆盖地区代替岗位工作地。若列表与详情矛盾，注明两处原文并按用户口径处理；未知与冲突分开，确认不可接受的异地岗位直接排除。候选汇报保留城市，避免只展示岗位名和薪资。

先判断业务匹配，再判断联系条件。未知或可协商门槛依用户口径处理，不能偷偷变成拒绝理由。明确不符写 reject；值得争取可写 shortlist；确需保留但不主动联系写 hold，并说明原因。完整详情失败不能写可发送的招呼，继续其他候选。

提交前对照排除理由与 SEARCH_PLAN：哪条用户规则、哪段 JD 支持这个结论？相关证据应保留原文含义、必做/优先的限定；不要补入 JD 未提及的工具、资格或要求。个人事实引用原材料，推断标明为推断。相似岗位采用相同口径，有不同判断要说明主要产出或明确要求的实质差别；不能因不同标题或某个词改变标准。

## 整体匹配优先，局部差距留作沟通

默认宽松保留值得争取的机会，用户明确的硬底线照常遵守。先概括岗位最主要的产出，再看用户直接经验与可迁移能力能覆盖多少，以及剩余差距是否真正影响主要工作。招聘方列出的“要求”不自动等于用户同意的一票否决条件。

在 reasons 中简短写出整体匹配程度、主要匹配证据和局部差距；可以由 Agent 给粗略匹配比例或区间，明确这是基于职责重要性的估计，用于排序与解释，不是精确测量。不要把每条 JD 等权计数，不设统一的 80% 等淘汰阈值，不写脚本评分。百分比不能掩盖明确的用户底线冲突，也不能因少量不满足就否定大部分匹配。

主要工作有经历支撑、只缺某项辅助技能或工具经验时，按用户宽严口径保留，并把差距留作沟通；一项职责不能直接代表整个岗位。只有主要产出确实是用户不愿承担的工作，或有明确不可接受的硬冲突才 reject。若混合职责或相邻方向影响主要工作且用户尚未表达取舍，用 hold 带实际样本澄清，结论写回该用户的 SEARCH_PLAN；首批和后续遇到新问题都适用。不要为每个局部缺口重复提问，也不要把这些个人取舍推广成公共职业规则。

把本组判断放在一个可覆盖复用的私有文件，例如 W/tmp/reviews.json：

```json
{
  "items": [
    {
      "job_id": "岗位ID1",
      "stage": "detail",
      "decision": "shortlist",
      "reasons": ["岗位的具体职责，与用户哪项真实经历对应"],
      "unknowns": ["尚未确认的条件，留在内部报告"],
      "evidence": [
        {"source": "user/materials/材料", "claim": "材料能够证明的本人贡献"},
        {"source": "job.detail.job_detail", "claim": "JD 对应的具体职责"}
      ],
      "greeting_draft": "用户确认的优势开头，相关经历与具体岗位匹配点，自然邀请看简历或交流。"
    },
    {
      "job_id": "岗位ID2",
      "stage": "detail",
      "decision": "reject",
      "reasons": ["完整 JD 中与用户目标明确冲突的主要职责"],
      "evidence": [{"source": "job.detail.job_detail", "claim": "支持排除理由的实际要求"}]
    }
  ]
}
```

```text
PY BOSS --workspace W review --file <私有文件的绝对路径>
```

也接受 JSON 数组、单条对象或每行一个对象的 JSONL。每条带 job_id、stage、decision 和实际理由；stage 只能是 list/detail，decision 只能是 shortlist/hold/reject，不能写 stage=hold 或漏 decision。含招呼时要有匹配依据。不需要 packet_id 或手抄 hash。

程序只保存 Agent 已作出的判断，返回 saved、failed、failed_ids 和逐项结果；任何条目失败时退出码为 1，输出仍保留成功记录和失败原因。先核对本组应保存的岗位与结果，再仅修正、重交失败项。失败项没有审查结论，不能计入“已审完”；部分失败不撤销成功项，也不需要把整组重新提交。

匹配但仅活跃过久时仍提交 stage=detail、decision=shortlist，由程序按活跃证据保存“合适不活跃”；不把活动状态写成 stage。未知可准备招呼。话术沿用 OUTREACH.md，选最相关的经历与岗位匹配点，不仅复述统一优势或堆砌专业术语；不虚构事实、不默认以职责问题结尾。细节见 [招呼流程](outreach.md)。

## 首次校准：验证策略，再确定发送范围

首批是用实际岗位检验双方对方向和宽严的理解，不是把初步推断全部定成淘汰结果。默认完整审查 10 个，聊天中展示所有实际结果和拟发送招呼，不只挑合适的一条。

报告先简要回顾首次确认的职业定位、优先/可接受方向、薪资/地点等硬条件和招聘门槛宽严；后续用户已有明确修订时说明变化并按最新口径对照。再呈现实际岗位结果、对应的匹配证据或硬冲突，以及哪些是待校准的边界。把“已确认策略—实际判断—建议调整”放在同一条报告里，用户无需翻旧消息或文档才能核对；无需重抄整份简历，也不能把建议调整写成已确认规则。

对新增疑点区分：

- **用户口径尚未对齐**：例如混合职责是否接受、某项要求能否用已有经历替代。展示代表岗位的实际职责、初步判断、分歧与建议，集中询问会影响结论的取舍；必要时邀请补相关项目证据，不强制补材料。涉及项先用现有 decision=hold，在 reasons/unknowns 写清“待用户校准什么”，不直接 reject。
- **招聘事实尚未说明**：例如工作制、实际报价、团队分工。按用户已确认的宽严处理，留作向招聘方核实的问题；不让用户猜公司事实，也不把未知自动升级成淘汰条件。
- **已有明确规则与事实**：直接执行，不借校准重复询问区间命中、已忽略的学历等已知口径；确有硬冲突时可排除并给出依据。

有影响结论的未对齐点，可以在不足 10 个或没有可联系者时先讨论。preview 的 ready_for_confirmation 只表示能否进入消息授权，不限制向用户展示当前样本或提问；不要为数字继续盲目补采补审。没有这种策略疑问且没有一个合适可联系者时，再加 10 个，直到至少有一个，并做完当前组。失败另计，真实不足或页面中断时如实报告。

用户对本次待定项明确反馈后，把规则/证据更新到对应资料，按其反馈继续这些岗位并批量保存新判断；原结论留在数据库历史里，不重开其他历史岗位。可复用仍有效的完整详情。用户已明确修订规则就记录原话，不再索要同一确认。校准后展示待发送全文，取得实际消息范围授权，再按每组 20 个审完、保存并串行发送合适者继续。

审查结果在库里，取待审就能继续。首批尚在等用户校准时，在 USER.md 留下待回答的问题与当前阶段，相关 hold 的理由和事实查 reviews，不另建问题状态机；新会话先承接未解决问题。未保存的小批次因中断丢失可以重审，不登记“正在审”“已认领”等状态，也不维护永久批次列表。已经保存的草稿可用 jobs --unsent、reviews --ids 查询，不会因新会话丢失。

## 历史由用户控制

当前未审岗位按最新要求审查。已保存的结论不因资料、话术、规则、岗位字段、在线状态、日期或 Skill 版本变化自动作废，也不自动重新投递。重复采集更新最新岗位事实和来源，保留历史判断与沟通记录。

仅在用户明确要求重审时，对指定岗位执行：

```text
PY BOSS --workspace W review-reset --ids <用户要求重审的ID...> --reason <用户实际要求>
```

该命令保留历史结论，将指定岗位恢复待审并要求重新获取详情；不重开 sent、contacted_external、already_contacted、sending/uncertain。随后照常取待审处理。不要因为程序升级、调整一句话或发现在线而自行运行此命令。

发送前的即时页面核实仍保留：发现已经沟通过、页面读取失败、活跃明确过久或 JD 与所用草稿不一致时，本次不发送。它不触发整库重审；需要重做某个已保存的判断时按用户要求处理。
