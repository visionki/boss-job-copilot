# 首次校准、模拟招呼与批量处理

先按 [审查说明](review.md) 获取完整 JD，由 Agent 保存判断、理由、证据和招呼。表达以当前用户确认的 OUTREACH.md 为准，事实来自 PROFILE.md/材料。模拟仅针对消息，不点击立即沟通；真实详情读取与审查照常。

## 招聘方活跃度与沟通额度

完整详情先判岗位是否合适，再看招聘方活跃。默认 week：在线、刚刚、今日、3 日内、本周活跃及未知可沟通；只有明确超出范围的匹配岗位才标 matched_inactive，例如本月、数月或半年前。未知不伪填在线；明确过久也不等于岗位已经停招。

详情在可见招聘方卡片读取 `.boss-online-tag` 和 `.boss-active-time`，优先明确在线标签，记录原文、来源和观察时间。不从 JD 猜活跃。标签不是准确最后登录时间，也不能证明消息排名。

列表 JSON 的 bossOnline=true 是当时在线的正面证据，false 或缺失不能推断今日不活跃。当前已核验的列表字段不包含完整天数标签；不要猜测 APP 的活跃选项是网页 URL 参数。

```text
PY BOSS --workspace W outreach policy
# 用户明确调整范围时，同时更新其方案：
PY BOSS --workspace W outreach policy --activity week
```

可选 today / 3d / week / month / any，累积包含更近期标签，均保留未知；any 不按活跃筛选。配置仅用于本地联系判断，不改变网页搜索。

**历史暂缓由用户控制。** 保存 matched_inactive 后，跨日、再次采集在线、标签变化、规则变化和升级都不自动恢复待审。只更新最新观察，保留原结论；用户要求重审时用 review-reset 恢复指定岗位，再读新详情和重新判断。旧 matched_activity_unknown 等历史记录同样保留，不自动迁移为候选。

对已审且尚未联系的正常草稿，发送前会读取当前详情和活跃；昨天“今日活跃”不是今天的发送依据。若 JD 已明显不同则本次不发，保留历史判断；明确过久则记录合适不活跃并继续其他岗位。完整 JD 读成功但标签仍未知可联系，详情读取失败不能用“未知”放行。

BOSS 的实际沟通额度以平台提示为准，不写死每天可发多少，也不把本工具 sent 数当作整个账号的剩余额度。明确限发就停相应网页动作，可继续本地分析；不降低匹配要求或绕过限制。

## 首次 10 个，无合适者再加 10 个

首批通过 jobs --unreviewed --view review --limit 10 取待审，相关或不确定者读取详情，由 Agent 判断。首轮默认 initial_review_count=10；没有未对齐的策略问题且 10 个完整审查没有一个合适可联系者时，再审 10 个，直到至少有一个，并完成当前组再展示。10 是校准步长，后续日常每组取 20 个，均不是整轮详情或消息配额。按 [首批校准](review.md#首次校准验证策略再确定发送范围) 用实际样本澄清新问题；提问和策略验证不受凑满数量或已有可发送者限制。

合适、不合适、详情已审但待用户校准、合适不活跃都算已完成详情审查；待定用 hold 保留且不发送。读取失败、只有列表判断、已读但尚未分析不算。列表明确排除者保留列表结论，从新候选补足详情数，不重读它来凑数。遇到“继续沟通”跳过消息，尚未审过的不要计成已审。局部失败另计，可补其他候选；真实候选耗尽、页面不可用或用户暂停时报告实际缺口。可用缓存尚未分析时应先完成分析。

没有另一个需登记或恢复的首批任务：候选 ID 来自本次查询，结果在库里，报告按需查库生成。中断后可查最新 reviews 或重新取待审，未保存的小批次可以重审。

```text
PY BOSS --workspace W outreach preview --ids <本次累计审查及失败的ID...>
# 用户需要文件时才显式导出：
PY BOSS --workspace W outreach preview --ids <ID...> --out <报告.md的绝对路径>
# 只有真实不足或浏览器中断，才说明实际原因：
PY BOSS --workspace W outreach preview --ids <ID...> --partial-reason <实际原因>
```

preview 直接返回每个公司的岗位链接、城市/区域、工作地址、薪资、公司规模、活跃、判断、理由、证据、待核实项及全部拟发送招呼，供聊天展示；默认不写 Markdown。仅保存用于绑定消息授权内容的 JSON 快照，岗位事实和结论仍在数据库，快照不作为工作流进度。需要留档或分享文件时再用 --out 导出，不把导出当成每批必做步骤。

聊天中先附已确认的职业画像与求职策略摘要（包括用户后续明确修订），再直接列出**全部累计结果概览和所有拟发送招呼全文**。对照策略解释保留、排除、待定的依据及建议调整，让用户同时核对策略和实际执行；不能只列结果再问是否发送，也无需打开文档或翻历史消息才能确认。存在新口径疑问时先询问，不把初步推断展示成已经定案的淘汰。已确定的规则不重复问。分别统计列表排除、详情已读/已审、待定、失败和可联系数量。有未审完、匹配者尚未写招呼或需要新详情者时不能授权发送，但随时可以讨论当前样本；partial-reason 不能将未完成分析伪装成缺口。全部不合适时不能假造合适者来启动发送。

## 自然的招呼与用户反馈

默认结构是：**重要优势 → 相关经历/成果 → 与岗位具体职责的匹配 → 邀请看简历或交流**。短问候即可，重要的真实优势建议靠前。用户认可的关键优势在按岗调整时保留，不把所有人写成同一种身份。

主体可以复用，从用户材料中选最贴近该岗的经历/成果，按 JD 调整匹配句；经历与匹配可合成一句，避免堆专业术语或仅泛称“匹配”。关键优势保留，不能为所有岗位复述同一串能力而漏掉相关的项目证据。默认不以职责比例、工作占比等问题结尾，疑问留在内部报告；用户明确希望先问条件时遵从其要求。

首批用于校准筛选口径和表达。有反馈时，事实写 PROFILE/材料，条件写 SEARCH_PLAN，话术写 OUTREACH/例句。后续未审岗位使用最新要求；过去结论不自动作废。若用户要求修改本次尚未发出的草稿，更新指定记录并重新展示，不需要清库或重抓所有岗位。

## 取得实际授权，然后每组审完发送

用户明确允许发送后才登记其原话，不要求固定口令。先让用户看具体结果与消息，明确是“只发这些草稿”，还是“发送首批，并按相同标准继续本轮队列”。单纯喜欢文案、登录、上传简历或沉默不等于发送授权。

```text
# 只同意本批已展示草稿，默认 scope 也是 batch：
PY BOSS --workspace W outreach authorize --preview <预览ID> --scope batch --user-message <真实原话>
# 也明确允许按同一标准持续处理本轮库内队列时：
PY BOSS --workspace W outreach authorize --preview <预览ID> --scope queue --user-message <真实原话>
PY BOSS --workspace W outreach send --id <岗位ID>
PY BOSS --workspace W result --id <请求ID>
```

authorize 只记录实际权限，不发送。batch 仅授权报告中拟发送的岗位和消息原文；改了稿必须展示新稿并取得相应授权。queue 包含授权时库内的岗位 ID，不能自动扩大到后来新采集的岗位；用户明确扩展时按实际范围处理。已有同范围授权跨会话沿用，不每批再问，也不重复登记来悄悄扩大范围。

先串行处理首批可联系者；之后**取 20 个 → 详情与审查 → 批量保存 → 串行发送本组合适者 → 再取 20 个**，使用 jobs --unreviewed --view review --limit 20。列表明确不符就记录排除，详情不符也记录排除；匹配但明确过久保留暂缓。单岗失败或待核实不阻塞其他岗位。只有 batch 授权时，本批之外仍只分析与保存草稿。

新会话先看最新用户指令和停止条件，接续未发草稿可查 jobs --unsent --view review --limit 20 与 reviews --ids；审查进度直接查 jobs --unreviewed --view review。没有首批发送游标、任务认领或恢复状态，必要的审查和实际联系记录独立保存。未保存的分析允许重做，已经发送或结果不确定的消息不能重发。

`outreach simulate` 撤销当前发送授权，保留草稿与历史记录。用户更新要求或升级 Skill 不会自动清历史、重开岗位或扩大权限；用户明确撤销、收窄或改变已授权行为时，助手应遵守最新指令。

用户指定“发 N 个就停”等范围时，把这条指令留在必要交接中，用本次范围的数据库联系记录核对完成量。sent 与 uncertain 分开报告，不能为凑成功数而在结果未明时多发。达到停止点后执行 outreach simulate 撤销本次授权，保留草稿和历史；不能因 queue 授权仍在就继续。这里没有新增默认额度或调度状态，未指定数量时仍按授权范围处理。

## 发送识别与防重复

Agent 调用 send 前，核对该岗实际工作城市/地址、薪资和公司条件与已确认底线，不能仅依赖搜索参数或“已入选”的旧印象；相互矛盾的事实未处理清楚时不擅自假定满足。send 串行访问对应岗位，检查当前完整详情、活跃和沟通按钮。**“继续沟通”直接跳过，不点击或进入会话补发。** 正常 details 读取也会记录这一事实。

| 沟通记录 | 含义 |
| --- | --- |
| sent | 本工作目录 Skill 发起，已核实定制消息，不重复发送 |
| contacted_external | 已显示继续沟通，本库没有 Skill 尝试；可能是手动、历史或其他方式，不猜具体来源 |
| already_contacted | 招聘方等已有记录去重，兼容历史，不计为本次 Skill 发送成功 |
| sending / uncertain | 已尝试但结果未核实；保留待核实，不补发 |

这些是实际联系事实，不是审查任务状态。发现继续沟通也不能把 sending/uncertain 改成“手动已发”，或覆盖已经核实的 sent。跨采集、规则变化和重审都保留联系记录。

暂停、关闭或重开浏览器不修改联系记录。中断前已保存的 sending 尝试继续保留，只读 verify；浏览器请求的 stopped/closed 回执不代表该岗位发送失败，也不能作为重发依据。

只有真实授权后才点立即沟通；在目标身份对应、输入全文一致时点击发送，通过普通页面操作，不调用或重放隐藏发送 API。发送前保存尝试记录，避免中途断线导致重复联系。

点击立即沟通后，可能出现详情页弹窗，也可能进入完整聊天页；两者均是正常入口，不因进入 `/web/geek/chat` 就重启浏览器。脚本兼容当前标签跳转和本次点击新开的聊天标签。完整页 URL 没有岗位/招聘方 ID 时，必须等公司、招聘方、岗位全名及左侧选中联系人全部与本次授权对象对应，才填写；发送前再次核对，不能仅凭输入框存在就发送。身份不符、页面尚未加载完整或存在多个匹配会话时，保留该次尝试，继续其他可处理项。

核实必须看到正确会话中的相同己方消息；平台默认招呼不是定制消息成功证据。详情弹窗读取“已发送”及消息 ID，完整聊天页只读当前会话的己方消息，区分正文和送达状态。最长等 45 秒，确认即返回，不是固定等待。超时保留发生阶段、当前身份和已有证据，不能把点击当成功。waiting_chat 且 send_attempted=false 表示尚未执行自定义消息发送，不代表浏览器卡死，也不能据此自动重发联系。

不确定时只读核实当前页，不点击继续沟通或发送：

```text
PY BOSS --workspace W outreach verify --id <岗位ID>
PY BOSS --workspace W result --id <请求ID>
```

verify 不恢复发送权限；查不到就保留 uncertain，继续其他候选。完整聊天 URL 缺 ID 时，只有公司、招聘方、岗位全名、选中会话及完整己方消息全部对应才作只读恢复。不要点击“继续沟通”重试、按名字遍历联系人或替旧 uncertain 自动补发；上述完整页发送兼容只用于已授权的新联系动作。

## 收尾

持续到用户约定的停止点、本轮可处理岗位为空或有实际中断，按需 report 汇总：采集缺口、详情已读/已审、排除/暂缓/失败、待发草稿、Skill 已发、历史已沟通和发送待核实。数量从数据库查询后统计，区分本次与历史记录，不手算或按消息条数代替岗位数。没有每岗写文档的要求，也不为凑齐漏页拖住后续步骤。正常结束保留窗口，交接只记用户需要知道的信息。
