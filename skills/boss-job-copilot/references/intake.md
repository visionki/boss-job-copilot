# 背景分析与方案确认

用户说“帮我找工作”时先走此流程；已有同方向、同范围的明确确认则接续，不重复访谈。只做职业分析、只开浏览器或手动登录是独立意图，不自动触发采集。

完整求职流程中，浏览器准备与本节材料分析并行推进：确定当前工作目录后，尽早按 [运行方式](operations.md#浏览器和登录) 打开或复用专用 BOSS 窗口，检查一次登录，不等画像和方案写完才开始准备。未登录可提示“BOSS 窗口已打开，你可以先手动登录；我继续分析简历和项目，随后一起核对职业画像与求职策略”，然后继续分析，不结束本轮去等登录。若环境准备未完成或浏览器故障，简述情况，仍继续可做的背景分析。不反复轮询登录或为准备而搜索岗位；明确只做分析、暂不开浏览器或只开窗口时，按该意图执行。

## 阅读材料与逐步澄清

先读当前数据目录的 USER.md 及其引用，保留用户实际陈述与材料出处。可使用简历、项目/作品说明、脱敏文档、用户口述、面试复盘；是否补材料由用户决定，不索取无关身份信息或强制提供保密原件。

围绕会改变方向判断的信息分轮提问，不把模板表格一次性全部发给用户：

- 用户的实际职责与当前状态：擅长和愿意继续做什么、希望改变什么、期望承担的责任、到岗时间等与求职相关的限制。
- 选代表项目/作品核实服务对象、解决的问题、本人贡献与团队分工、关键取舍、交付与持续负责的范围、可验证成果及来源。把“参与过”与“独立负责过”分开。
- 希望寻找的实际工作：核心产出、日常工作、责任范围、混合职责的接受度、专业与管理路线；再映射为岗位名称和搜索词。
- 地区、通勤/远程、薪资口径与目标、工作制、公司与团队偏好，以及哪些是底线、哪些可交换。
- 执行策略：广覆盖批量求职还是少量精选，预期整轮覆盖规模、可接受的沟通核实项与何时汇报。用户已说海投或广泛尝试时复用该偏好，不再追问同一选择；未明确时可提出广覆盖方案供其确认。
- 招呼偏好：可询问喜欢的语气、长短、希望优先突出的优势或参考例子；已有偏好直接沿用，没有明确偏好则根据简历先拟一版参考稿，随方案请用户调整。

对宽泛岗位名称，依据当前用户材料、实际工作对象和主要产出提出候选拆分，再让用户确认。同名岗位可能承担不同工作，名称不同的岗位也可能职责相近；一项辅助任务不直接代表整个职业方向。哪些相邻方向可接受、哪些混合职责需要澄清，只写在该用户的 SEARCH_PLAN，不放进公共 Skill 作为职业白名单或排除规则。

材料不足时写出有限结论和待核实项，不包装成完整能力评价。用户想先探索市场，可提出小范围探索方案，把暂定方向、已知缺项与试采范围写清并确认；不以“先看看”为理由跳过确认。

提取简历或项目时保留数值、单位、时间、统计口径和贡献归属；活跃用户与累计用户、千与万、团队成果与个人职责不能混用。原文乱码或数字不清时回到原件/渲染页核对，不能凭印象补全。对外要引用的量化优势再核对一次出处，材料没有写出的技能与成果不补成事实。

用户已明确方向并希望批量求职时，不再默认缩成“小范围探索”。明确策略和硬条件后，用多组相关关键词与范围覆盖机会；只有用户选择精选或确有方向不确定性时才把少量样本作为整轮目标。

## PROFILE.md：可供用户自我分析的职业画像

使用 `assets/PROFILE.template.md`，结果保存到所选数据目录的 `user/PROFILE.md`。该文档不只是简历复述，应包含：

1. 已知背景、现状与材料版本；区分事实、用户目标、助手推断和未核实内容。
2. 代表项目的证据链：问题 → 本人行动/决策 → 结果 → 可支持的能力 → 证据限制。
3. 有证据的优势与差异点，适合贡献的场景；避免空泛评价、夸大成果或编造数字。
4. 能力边界与欠缺证据，区分“未展示”与“不会”；可迁移能力和希望发展的能力分开。
5. 候选方向及理由、可能需要补强的能力和用户愿意/不愿意做的工作。建议尚未确认时不能写成既定目标。

画像不能只保存在文档里。完成初步材料分析后，按下方首次确认报告在聊天中展示足以核对的定位、优势、方向边界和依据，并与求职策略一起接受纠正；需要承接的背景和项目证据沉淀到 PROFILE，不让用户先阅读文档才能讨论，也不为每次回答重写所有资料。身份指职业背景与职责定位，不需要推测年龄、性格或私人状态。对外可引用经历与内部分析分开，后者不直接写进招呼。

## 首次确认报告：职业画像与求职策略一起核对

这是首次材料分析完成后、开始采集前的一次联合确认，沿用 plan confirm，不增加独立的画像审批或状态。默认直接在聊天输出，必要资料分别存 PROFILE、SEARCH_PLAN、OUTREACH；用户需要文件时再导出，不额外维护一份重复的长期报告。

报告用易读的分段或表格，完整表达以下内容，篇幅随材料多少调整：

1. **我对你的职业定位**：一句话定位，再说明经历主线、本人通常承担的职责、希望继续和希望改变的工作。当前能力、求职意愿与助手建议分开，不把新方向覆盖掉既有经验。
2. **核心优势与证据**：选与求职有关的优势，各连到代表项目、本人做过的事或可核实成果；既呈现用户认可的重要优势，也指出证据不足之处，避免只列专业名词。
3. **方向与边界**：分别列优先方向、可接受的相邻/混合方向、明确不考虑的核心职责，解释与用户经历和意愿的联系。尚未表达的取舍标待确认，不擅自把某种身份、语言差异或行业背景变成排除条件。
4. **实际筛选策略**：地区、薪资口径与底线、工作制、公司偏好，以及学历/年限/专业技能/工具等要求各按严格、可协商、忽略或待确认中的哪种口径处理。讲清职责整体匹配与局部差距如何判断，哪些事实缺失留待沟通。随后列搜索词、网页筛选、每组页数和首批验证方式，让用户看见画像怎样变成检索和判断。
5. **对外表达**：给出一段职业介绍或招呼参考稿全文，保留已确认的主要优势，说明与目标工作的关联，便于用户检查是否准确自然；可以与 OUTREACH 参考稿共用，避免再写一份重复长文。无实际 JD 时不声称匹配某家公司。
6. **需要你核对的点**：指出最可能影响方向的推断或缺项，邀请纠正定位、相邻方向和条件宽严。已有明确回答不再重问，材料少就如实展示有限画像，不为了填满格式编造信息。

确认问题同时覆盖画像与策略，例如“以上对你的定位、优势和可接受方向是否准确？这些筛选宽严和搜索范围是否符合你的想法？”让用户在同一条报告里核对，不能仅问是否按参数开搜。确认这一份即可继续已说明的采集与首批审查，发送仍需要实际消息授权。

报告末尾同时简述已观察到的浏览器准备情况，方便用户核对方案时顺手登录；未检查成功就如实说明，不能从窗口已打开推断登录。登录提示只是准备提醒，不增加一轮必须回复的确认，也不把它写进 SEARCH_PLAN 正文造成方案反复变化。用户认可方案后检查一次实际页面并读取结果，已登录即可采集；仍未登录或有验证时才等待人工处理。用户只说“已登录”则继续尚未完成的方案确认。

用户后续补充经历或改定位时，直接展示修订后的画像和受影响的策略；其明确修改并要求继续，按该原话执行，不再重复求确认。用户若明确说先看画像、先不审岗位或不发送，就停在展示阶段，不能用先前权限越过当前要求。新会话已有同方向的确认时先承接必要进度，不强制从头重做报告。

## 两类条件，分别确认

**用户自己的期望**：底线 / 优先考虑 / 不限制 / 待确认。例如工作地点、报酬、工作制、职责内容或公司类型。期望薪资不是自动的最低底线。

**招聘方的门槛**：区分学历、专业、年限、行业履历、专业技能与工具等的处理口径。已有信息直接提取，只集中询问会影响判断且尚未明确的宽严，不照表逐项重问。

| 口径 | 列表与详情审查行为 |
| --- | --- |
| 严格遵守 | 有明确且不可满足的冲突才据此排除；信息缺失先待核实 |
| 允许协商/能力替代 | 保留合适岗位，列出差距与相关项目证据，后续沟通核实 |
| 不据此筛除 | 不作为网页过滤、扣分或拒绝理由；仍如实记录，不伪造资格 |
| 待确认 | 先问清策略；不得默认为严格或宽松 |

每一项可采用不同口径，允许附适用范围和例外。一个学历字段、技能关键词或年限差异不是自动拒绝的理由；某项被允许放宽也不代表所有要求均可忽略。职责本身与用户目标冲突，要按用户已确认的方向处理。

首次访谈无需穷尽所有边界。首批真实岗位可能暴露此前没想到的混合职责、技能要求或可迁移经历；这时带具体样本和建议重新对齐，允许用户补充背景或选择宽严。没有依据的从严推断先保留待定，不能先大批淘汰再仅询问是否发送剩下一条。已确认的默认规则直接执行，不重复发问；招聘方未写明的事实按已确认口径留待沟通，不向用户索求公司的未知事实。

广覆盖的门槛是“职责方向相关、有真实经历可以争取、没有明确硬冲突”，不是所有偏好都已被证实。未写明工作制、薪资细节或团队职责时，可以保留并准备沟通问题，不把未知变成默认淘汰。只有用户明确要求某项先核实再进入候选时才据此暂停该岗位；其余队列继续处理。优先级影响先后顺序，不等同于只保留最优几个。

方案默认说明整体匹配优先的宽松口径：主要职责大部分有直接或可迁移经验，局部技能缺口可在沟通中核实，不按每条招聘要求逐项否决。用户可明确选择更严格的范围。匹配程度由 Agent 综合职责重要性解释或粗估比例，作为排序参考，不使用程序评分或统一淘汰线。

网页参数筛的是招聘岗位，不是用户自身属性。学历等可协商项可不作硬筛；已明确且网站支持的条件须落实到配置。薪资选择一个覆盖目标的档位，跨档按期望上端向上选，用 filters salary --target 查询，不分别搜索。方案展示实际过滤项及有意省略的理由，不能默认漏掉薪资。

## 薪资区间的默认初筛规则

岗位薪资按标示区间判断，用户目标按单值或区间判断。在可比较的同一口径下默认采用以下规则，不额外问用户是否接受区间命中：

- 单个目标 `T` 视为 `[T, T]`；岗位 `[J低, J高]` 满足 `J低 <= T <= J高` 即命中。
- 用户给出目标区间 `[T低, T高]` 时，两区间有交集即命中：`max(J低, T低) <= min(J高, T高)`，端点相等也算。
- 不要求岗位下限达到目标，也不要求岗位区间完整覆盖整个目标区间。例如目标 30K，岗位 20–30K 或 25–45K 均可；目标 28–32K，岗位 25–28K 或 30–45K 也可。数字仅示范规则，不是任何用户的预设目标。
- 岗位区间整体高于目标时，不因无交集自动排除，结合职责继续审查。整体低于目标则标注“低于目标”，按已有方案的硬底线或允许下探范围处理，不把目标偷偷改成已确认底线，也不逐档重复问是否保留。

在国内全职求职、上下文以 K 讨论月薪且用户未另作说明时，初筛可暂按税前月薪处理，在整轮方案里注明即可，不为这项常规口径另开一轮提问。用户明确给出税后、年包、日薪、时薪或其他单位时按其说明；口径冲突无法可靠比较的岗位标记待核实，不强行换算或判定不符合。

区间命中只表示值得沟通，不保证招聘方会按区间上限报价；实际报价、固定与浮动部分、薪数和奖金留待沟通核实。薪资面议、缺失或无法解析也保留未知，不视为零薪资。把规则直接写进方案并随整轮方案确认；只有用户明确要求更严格的薪资匹配方式时才覆盖默认，不把通用区间规则再变成单独的必答澄清题。

## 招呼偏好与参考稿

在开始搜索前，用 `assets/OUTREACH.template.md` 整理私有 `user/OUTREACH.md`，保存用户偏好、开头优先保留的优势及依据、参考稿和反馈。建议将与目标相关的重要优势放在开头，例如有依据的经验、代表作品或成果；具体选什么由当前用户背景和偏好决定，不预填他人的年限或项目。

结合简历与已知方向写出一版自然、简短的自我介绍，包含重要优势、相关经历、匹配点与交流意愿。此时尚无实际 JD，匹配点先说明经历与目标方向的关联，不声称已匹配某家公司；后续读到岗位后按确认的结构少量调整经历与具体岗位匹配句，无需每岗重新设计整段话术。用户明确要求的表达优先，内部职责疑问不默认放入首条招呼。

把参考稿全文随搜索方案一起展示，邀请用户修改语气、开头重点或结尾；不要只给模板链接，也不用单独增加一轮风格问卷。用户确认整份方案及所展示的参考稿后继续；首批真实岗位仍照常展示完整审查和拟发送消息，另按实际授权发送。

## SEARCH_PLAN.md：可确认的搜索方案

使用 `assets/SEARCH_PLAN.template.md`，保存到 `user/SEARCH_PLAN.md`。它是当前方向与筛选口径的唯一规则来源；USER.md 只链接并记录阶段，避免多份互相冲突的条件表。

按上方首次确认报告把职业画像与方案放在同一条聊天中，至少说明：

- 已知背景与优势、建议主方向/相邻方向、明确不考虑的职责，以及哪些仍是推断。
- 实际数据目录；城市/区域、通勤/远程；薪资口径；公司与团队偏好。
- 用户底线、可协商条件和招聘门槛的宽严矩阵；缺失或矛盾信息如何处理。
- 招呼偏好、建议放在开头的重要优势，以及一版基于当前资料写好的参考稿全文；让用户和搜索方案一起确认是否需要调整，具体内容维护在 OUTREACH.md。
- 准备用的关键词与组合、网页筛选项，以及故意留给详情/沟通判断的项目。可附私有搜索 JSON 与离线预览，但不能只给用户看枚举值或命令。
- 整轮策略与工作量：广覆盖/精选、覆盖的组合及每组页数。未指定时每组最多 10 页（含第一页），用户有指定则按其要求；随方案说明默认值，不另外追问常规页数。默认完成本轮全部列表初审及筛出的候选队列，不能自行缩成前 N 个。列表达到页数上限或提前无下一页时结束，覆盖目标不是保证结果数量。
- 页面节奏默认串行、每次间隔 5 秒，无小时/每日配额、任务总时长和详情数量限制；直接随方案说明，不单独追问常规节奏。首个页面的数据校验与为便于分析而分批，不改变整轮覆盖与处理范围。
- 采集允许缺页，结束或无法继续时处理已有及新增待审。通过 jobs --unreviewed --view review 取数据，首批 --limit 10，后续默认 --limit 20；Agent 初筛、读详情并判断，结果批量入库。首批目标 10 个详情审查，列表明确排除者以新候选替补；遇到尚未对齐的判断边界先用样本澄清，无此问题且没有合适可联系者才再加 10 个。聊天展示累计全部结论、待校准项、理由与招呼全文，用户校准并授权后先发首批，再每组 20 个审完并发送合适者。数量可按要求调整，不是整轮上限；用户另定发送数量或停止点时优先遵守。搜索确认与发送授权分开记录，不上传简历或执行其他申请。
- 正常采集和初筛，完整详情先判是否合适，再看活跃。默认本周活跃以内与未知均可招呼，只有明确超出范围者暂缓。标签未知不视为离线；岗位名称、技能标签不代替 Agent 的职责判断，相关或不确定者尽量读详情，区分主要产出、必做与加分项。历史审查和暂缓记录保留，不因再次采集在线或规则变化自动重开；仅用户要求重新审查时恢复指定记录并读取新详情。直接随方案说明，不承诺网页原生提供 APP 活跃过滤。

确认同时覆盖职业画像和整轮策略，例如“以上职业定位、优势、可接受方向和条件宽严是否准确？这版对外表达有没有需要调整的地方？”有关键缺项先澄清，不把确认按钮当作对未知假设的默认认可。需要等待用户回复；上传简历、登录完成、沉默和超时都不是确认。用户认可后记下对应方案及其原话，再运行 `plan confirm --user-message <原话>`；不要自行构造同意，也不要求固定回复口令。确认功能不访问 BOSS。相同范围内下一页、下一批详情、正常的请求分段续跑都不重新索取确认；暂停或异常后的恢复规则仍需遵守。

新增材料按需补入 PROFILE.md。若改变搜索方向或条件，先暂停正在运行的采集，再修改 SEARCH_PLAN.md 并据用户实际指令确认；用户对本次边界的明确答复已经给出时，不为同一修改再问一遍。仅补证据、更新交接或重读同一方案，不反复求确认。岗位处理进度保存在数据库，USER.md 只留必要交接与资料索引；方案确认、首批待校准或待发送授权等关键阶段变更时简短更新，清除过时的“待确认”，不逐页记数。保持 SEARCH_PLAN.md 作为方案正文，确认后不用日常进度改写它。程序会因方案正文变化使旧确认失效，但无法判断文档语义或验证聊天原话，助手需对此负责。

确认前可做材料分析、本地资料整理、字典查询和 `--dry-run`，以及上述 BOSS 首页与登录准备；不执行岗位搜索、采集、详情读取或招呼发送。搜索方案确认和实际页面可用后才进入采集，发送另按实际授权执行。
