# 参数化搜索与列表收集

日常检索使用随 Skill 分发的 `scripts/bosslib/filter-catalog.json`，将用户要求转为参数。程序负责中文选项解析、URL、串行翻页、监听 JSON、去重和进度保存。无需为每次检索编写页面点击或 CDP 脚本。页面发生变化时才维护适配器与字典。

实际采集前必须有已确认的 `user/SEARCH_PLAN.md`，见 [背景分析与方案确认](intake.md)。确认前可查本地字典、准备配置和 `--dry-run`，不能因准备好参数就执行搜索。参数只能落实方案中同意的网页筛选项：用户自身学历/年限不是自动过滤值，可协商的招聘门槛不要提前窄化；网站不能表达的要求留给本地审查，保持用户已确认的宽严口径。

下文 `PY`、`BOSS`、`W` 的含义见 [运行方式](operations.md)。

## 查字典（本地，不访问网页）

```text
PY BOSS --workspace W filters list
PY BOSS --workspace W filters show city --contains 杭州
PY BOSS --workspace W filters show salary
PY BOSS --workspace W filters show position --contains Java
PY BOSS --workspace W filters show industry --contains 互联网
```

输出包含名称、代码、URL 参数、单选/多选和数量限制。长列表使用 `--offset`、`--limit`（最大 5000）。按名称或代码传值均可；重名时使用输出中的完整 `path`（`一级 > 二级 > 选项`）或代码，不猜映射。

2026-09-20 从正常搜索页响应及已渲染组件核验：城市菜单 373 项，职位分类路径 1098 条（848 个独立职位代码），行业叶子 145 项。同一职位可能出现在多个分类下，按代码合并选择；仅不同代码的同名选项要求消歧。这是当日网站提供的菜单，不代表中国所有行政区划；观察日期与来源记录在字典中。

| 参数 | 网站规则 |
| --- | --- |
| `--keyword` | 多个关键词分别搜索；不能为空，当前入口是搜索模式 |
| `--city` | 每次搜索一个城市；多个城市由程序拆分 |
| `--salary` | 只传一个档位；覆盖目标，边界或跨档按期望上端向上选，不拆分薪资搜索 |
| `--job-type` | 单选；不限、全职、兼职 |
| `--degree`、`--experience`、`--company-size`、`--stage` | 多选，逗号合并到一个 URL |
| `--position` | 多选；使用实际职位叶子选项 |
| `--industry` | 多选，最多 3 项 |
| `--area` | 城市下的区县/商圈，合计最多 9 项 |
| `--subway` | 城市下的线路/站点，合计最多 15 项 |
| `--pay-type`、`--part-time` | 兼职专用，多选；分别为结算方式、兼职时间 |

列表型参数支持逗号、中文逗号和重复参数；salary 例外，只能解析出一个档位。不限与具体项不能混用。公司规模可省略人，10000+ 对应 10000人以上；100-500 不会被当成 100-499。

兼职页面用结算方式和兼职时间替代薪资，且隐藏融资阶段。`--job-type 兼职` 不能同时传 `--salary` / `--stage`；传 `--pay-type` / `--part-time` 时必须明确选择兼职。

## 生成计划并执行

```text
PY BOSS --workspace W collect --keyword "岗位关键词" --city "北京,上海" --company-size "100-499,500-999" --salary "20-50K" --pages 10 --interval 5 --dry-run
PY BOSS --workspace W collect --config <搜索配置.json> --dry-run
PY BOSS --workspace W plan status
# 方案已确认后，才实际执行：
PY BOSS --workspace W collect --config <搜索配置.json>
PY BOSS --workspace W result --id <request_id>
```

`--dry-run` 完全本地：检查选项、组合、实际 URL 和页数。上例两个城市、一个薪资档位为两组，最多二十页。公司规模仍在同一组内多选。`filters salary --target <月薪K单值或区间>` 查询推荐的唯一档位；跨档或边界按期望上端向上选，不为薪资增加搜索次数。

新建实际采集任务必须明确一个薪资档位；漏填时 dry-run 返回提醒，实际执行在提交浏览器任务前拒绝。用户明确不限薪资时传 `--salary 不限`，不能把遗漏配置当成不限。兼职使用自己的结算方式过滤，不要求薪资档位；恢复旧批次沿用原计划。

以上城市、关键词和筛选条件仅展示语法，不是默认求职目标。向用户确认时用职责和自然语言说明整轮方案，不要求用户理解枚举值。先拟定相关搜索词与组合，用户未指定页数时采用每组十页并说明总量；不要机械地把几页试采当作全部工作。确认同一搜索范围后可分批执行，不需每页重复确认；更换方向、增加城市、改变门槛口径或扩大约定范围时先更新方案。

`--pages N`（别名 `--page`）始终表示**每组检索最多 N 页，包含第一页**，默认 **10**。一组是一个关键词、一个城市与一组实际筛选条件，网页单选项的多个值会继续拆分组合。只有实际收到并解析了匹配条件的列表响应才计页，按请求页号去重。达到设定页数即停止该组，网站无下一页时可提前结束；不默认一直翻到无结果。

用户指定页数时用 `--pages` 或配置文件的 `pages`；两者都省略才使用默认十页，续跑保留原计划页数。新环境用首个页面核验参数与数据，正常后继续已确认页数；只有明确的小批验收才单独设为一页，验收后另行执行整轮计划，不对已完成的一页批次反复 `--resume`。重复页由库去重，新增覆盖以实际唯一岗位数报告。

JSON 字段与 CLI 对应，但使用下划线：`keyword`、`city`、`salary`、`degree`、`experience`、`company_size`、`stage`、`position`、`industry`、`job_type`、`pay_type`、`part_time`、`area`、`subway`、`pages`、`interval`、`max_jobs`。选项可为字符串或字符串数组，CLI 显式值覆盖同名配置。配置属于用户目录，不写回 Skill。

`--interval` 是页面动作之间的秒数，默认和最低均为 5；用户明确要求更慢时可以增大。优先级为命令行 → 搜索配置 → 工作目录 `settings.json`（新建时为 5）。`--max-jobs` 是用户可选的每组岗位数上限；未指定则按页数收集，不自动添加岗位数上限。没有小时/每日访问配额和单次任务总时长限制。

## 区县、商圈和地铁

这些字典依赖城市，不批量遍历全国区域。首次使用 `--area` 或 `--subway` 时，程序正常打开目标城市搜索页，读取网页已加载的公共数据，缓存到 `W/filters/regions/<城市码>.json`，再生成最终 URL。准备字典的导航遵守同样的 5 秒间隔，不算收集页；准备阶段的宽范围列表不入库。

```text
PY BOSS --workspace W collect --keyword Java --city 北京 --area 海淀区 --salary <已确认的档位>
PY BOSS --workspace W filters show area --city 北京
PY BOSS --workspace W filters show subway --city 北京
```

可用名称、代码或 `父项 > 子项`；同名站点须明确线路。带区域筛选时一次只指定一个城市，避免把一个城市的区域套到另一个城市。

## 进度、恢复与页面变化

页面动作共享 profile 的最近访问时间，至少 5 秒且串行。单条坏数据跳过、单组异常继续，结果中的 collection.state 可为 completed_with_gaps；报告真实覆盖，直接进入数据库审查。登录/验证/明确拒绝访问或用户暂停才停止对应网页工作。

```text
PY BOSS --workspace W collect --resume <run_id> --dry-run
PY BOSS --workspace W collect --resume <run_id>
```

恢复跳过已完成组合。当前窗口仍在经核验的原条件、原页码时继续翻页；否则未完成组合从第一页正常加载并去重，返回 `resume_mode`。没有直接重放接口或伪造跳页。恢复前核对停止原因；登录/验证按 [运行方式](operations.md) 处理，不循环重试。

结果中的 `batch` 是整次收集的批次 ID，恢复后沿用，用 `jobs --batch <batch>` 查询。请求 ID 标识一次提交，恢复请求可能有不同 ID。进度保存在 `runtime/collections/`。

**隔天重新搜索与中断续跑分开**：下一次更新岗位时，以相同配置提交新的 `collect`，从第一页收集当前结果、建立新批次并继续使用同一数据库。`--resume` 只接续尚未完成的旧计划；已完成计划不会重新收集。不得因为昨天已完成或库里已有岗位就跳过今天的数据更新，也不自动建立每日定时任务。

维护命令：`filters refresh` 读取当前搜索页已加载字典，保存私有覆盖版本及区域缓存；`filters refresh --reload` 增加一次限速的正常刷新。日常搜索无需刷新字典。读取不完整或选项消失时停止报告，不当场生成临时点击脚本；分享新规则前核验并更新公共字典。

旧入口保留为 `filters snapshot` 与 `collect --filter-id <id>`，用于已有快照兼容，默认工作流使用参数。

## 入库后的分析

列表来自浏览器正常加载的 `/wapi/zpgeek/search/joblist.json`；被动接收响应，不模拟签名或重放请求。入库前核对请求筛选参数，忽略上一轮遗留请求。

列表正常获取、由 Agent 正常初筛，不因活跃度未知跳过匹配分析，也不写关键词过滤脚本代替职责判断；相关或职责模糊的尽量补详情。APP 的活跃筛选未核验为网页 URL 参数，不猜测映射。列表 bossOnline 只有布尔值：true 是在线证据，false 不能证明不活跃；详情 DOM 才读取完整标签。匹配且本周以内或未知均可继续，明确超出范围才持久暂缓。已保存的审查和暂缓不因新在线观察、规则变化或跨日自动重开；用户明确要求重新审查时才恢复指定岗位。摘要返回 recruiter_activity 和 activity_hold，见 [活跃规则](outreach.md#招聘方活跃度与沟通额度)。

岗位表按 `encryptJobId`（库中的 `id`）去重，跨页、关键词、城市与日期重复出现只更新同一条记录：保留首次发现时间，更新最近发现时间和当前列表字段，另存各批次/搜索来源，历史审查不删除。同公司同标题但 ID 不同的岗位仍分别保留。再次看到岗位仅更新事实和来源；字段变化可标记详情缓存待更新，但不会使历史审查作废或自动恢复待审，已沟通记录也保留。仅某次没出现在前十页不能证明岗位已下架。

采集正常结束、有缺页或提前结束后，都用 `jobs --unreviewed --view review --limit 20` 取本方向已有和新增待审；首批校准用 --limit 10，不要求补齐全部页。Agent 简短初筛，相关或不确定者读详情，每组完成判断并批量保存，按 [招呼流程](outreach.md) 发送获授权的合适者，再取下一组。`jobs --limit` 只是可调整的单次读取量，不作语义预选。

薪资档位是粗筛。已知目标时选择一个覆盖期望上端的档位，不默认留空或传多个档位。入库后按实际区间交集及 [薪资规则](intake.md#薪资区间的默认初筛规则) 判断。低薪备选默认 reserve，只有用户允许下探才进入主动详情/沟通队列。网页可能漏掉未标薪资机会，此取舍随方案说明，不因此默认取消过滤。
